## Beads Issue Tracker

This project uses **bd (beads)** for issue tracking. Run `bd prime` to see full workflow context and commands.

### Quick Reference

```bash
bd ready              # Find available work
bd show <id>          # View issue details
bd update <id> --claim  # Claim work
bd close <id>         # Complete work
```

### Rules

- Use `bd` for ALL task tracking — do NOT use TodoWrite, TaskCreate, or markdown TODO lists
- Run `bd prime` for detailed command reference and session close protocol
- Use `bd remember` for persistent knowledge — do NOT use MEMORY.md files

## Session Completion

**When ending a work session**, you MUST complete ALL steps below. Work is NOT complete until `git push` succeeds.

**MANDATORY WORKFLOW:**

1. **File issues for remaining work** - Create issues for anything that needs follow-up
2. **Run quality gates** (if code changed) - Tests, linters, builds
3. **Update issue status** - Close finished work, update in-progress items
4. **PUSH TO REMOTE** - This is MANDATORY:
   ```bash
   git pull --rebase
   bd dolt push
   git push
   git status  # MUST show "up to date with origin"
   ```
5. **Clean up** - Clear stashes, prune remote branches
6. **Verify** - All changes committed AND pushed
7. **Hand off** - Provide context for next session

**CRITICAL RULES:**
- Work is NOT complete until `git push` succeeds
- NEVER stop before pushing - that leaves work stranded locally
- NEVER say "ready to push when you are" - YOU must push
- If push fails, resolve and retry until it succeeds

## Verify a push or deploy by its EXIT CODE, never by a tail of its output

**Never judge whether a push, deploy, or build succeeded from a `tail`, `head`, or
`grep` of its output.** Check the exit code, or read the output in full. "Work is NOT
complete until `git push` succeeds" (above) means *verified*, not *no visible error*.

```bash
bd dolt push; echo "exit=$?"      # exit=0 is the only proof
bd dolt push || echo "PUSH FAILED" # or make the failure loud
```

⭐ **`bd dolt push` is the specific trap.** On failure it still prints a trailing
`Done` plus four generic credential hints, with the REAL error scrolled above them —
so `bd dolt push | tail -5` shows `Done` and reads as success. It is not.

**Worked example, 2026-10-28** (bead `flashgen-tr2`): `bd dolt push | tail -5` reported
`Done` while GitHub had actually rejected `refs/dolt/data` with **`GH013` push
protection** — an `AKIA`-prefixed AWS access key **ID** in a bead's text tripped secret
scanning. Two more pushes "succeeded" the same way before the full output was read. The
bead data silently stayed local the whole time.

**Two follow-ons from that case:**
- **GitHub secret scanning blocks `bd dolt push` on `AKIA`-prefixed strings** in bead
  text, even though an access key ID is an identifier and not a credential. Clear it via
  the unblock URLs printed in the error (reason: *false positive*), or keep key IDs out of
  bead text and reference the vault note instead. Dolt pushes whole chunks, so redacting
  after the fact does not help — the committed chunk still has to transfer.
- **Do not put an `AKIA`-prefixed string in a tracked file either** (this one included),
  or `git push` hits the same wall.

## `bd update --notes` REPLACES the notes field — use `--append-notes` to add

`--notes` sets the field. `--append-notes` appends with a newline separator. There is no
confirmation and no diff, so overwriting an earlier record looks exactly like adding to it.

**Worked example, 2026-10-28** (bead `flashgen-tr2`): four successive `--notes` calls across one
session silently destroyed a pre-change state record, a deactivation record, and a dated follow-up
checklist. Only the last note survived. It was reconstructed from scratch files that happened to
still exist — `bd dolt` history would otherwise have been the only route back.

Before replacing notes deliberately, read the current field first (`bd show <id> --json`), and
prefer `--append-notes` whenever you are adding rather than consolidating.

### Keep `AKIA`-prefixed strings out of bead text specifically

A dolt chunk carries the WHOLE ROW forward, so one such string in a bead's notes or description
makes **every future push touching that bead** fail GitHub secret-scanning until somebody clicks an
unblock URL — not just the push that introduced it. Redact to last-4 in the bead and keep the full
ids in the vault note. Redacting afterwards fixes future chunks but not the one already committed,
which still needs the one-time unblock.
